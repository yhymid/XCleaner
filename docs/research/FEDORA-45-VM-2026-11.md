# Fedora 45 Workstation in a VM: field data (2026-11-22)

**English** | [Polski](FEDORA-45-VM-2026-11.pl.md)

One-time, read-only data collection on a fresh Fedora 45 Workstation install (QEMU/KVM,
4 vCPU, 4 GiB RAM, 20 GiB disk), with an XCleaner build of commit `c5a5f01`. Raw outputs
(57 files) stay outside the repo on the owner's machine (`~/vm/data-fedora45/`). Root-only
areas were read with a temporary passwordless sudo rule that was removed afterwards.
Nothing was deleted by the collection itself; the only deletions are the owner's own clicks
on "Clean selected" (logged below) and a test install/remove of three packages.

## 2. XCleaner results

- `.rpm` built on fedora:41 installs and runs on Fedora 45; `ldd` clean.
- `--scan`: 2.0 s, 13 items, 153.4 MiB (91.0 MiB preselected). Same numbers in EN and PL
  (PL uses a decimal comma).
- GUI opens under GNOME Wayland. The EN/PL switch saves `lang=` to
  `~/.config/xcleaner/settings.txt` and rebuilds the window in the same process, both
  directions. Mesa warnings (`ZINK: failed to choose pdev`) come from the VM without GL.
- **Full clean incl. root tasks works.** XCleaner found Ptyxis by itself (despite the
  `xdg-terminal-exec` setting pointing at a missing binary), ran sudo there, and the history
  log shows 0 errors:

  | Item | Freed |

  | root: rotated logs in `/var/log` | 4.0 MiB |
  | root: coredumps | 588 KiB |

- Cosmetic: `event-sound-cache.tdb.<machine-id>.x86_64-redhat-linux-gnu` is shown under its raw

## 4. Gaps found in XCleaner

1. **dnf5 cache path.** On Workstation the cache lives in `/var/cache/dnf5daemon-server`
   (dnf5daemon, used by GNOME Software); `/var/cache/libdnf5` does not exist. `pkgcache.rs`
   only knows `/var/cache/libdnf5` and `/var/cache/dnf`.
2. **Offline update downloads, 1.5 GiB.** `/var/lib/dnf/offline/packages` plus
   `/usr/lib/sysimage/libdnf5/offline/offline-transaction-state.toml`
   (`status = "download-complete"`, `rpmdb_cookie = …`, `cachedir = …`).
   - No `/system-update` link yet, so the update was not scheduled for reboot.
   - A later `dnf5 install` printed "pending offline transaction was invalidated" (the rpmdb
     cookie changed). The 1.5 GiB then stayed on disk, while `dnf5 offline status` still
     suggested `dnf5 offline reboot`.
   - Rule proposal: never touch it while `/system-update` exists; otherwise offer it as
     *review* ("downloaded update, GNOME Software will download it again"), cleaned by the
     official `dnf5 offline clean` in the root helper rather than by deleting files
     (command name per dnf5 docs, to verify).
3. **Leftovers on Fedora.** Test: `dnf5 install mc ranger htop`, run them, `dnf5 remove`.
   `~/.config/ranger` stayed behind; XCleaner showed nothing. Removed-package evidence is
   read from `pacman.log`, `dpkg.log` and the zypper history (`pkgdb.rs`), but not yet from
   dnf5, whose history is SQLite. On Debian 13 the same test finds `~/.config/ranger`.
   - dnf5 keeps history in `/usr/lib/sysimage/libdnf5/transaction_history.sqlite`
     (+ `-wal`, `-shm`), mode 0644, readable by the user in read-only mode. Tables include
     `trans`, `trans_item`, `rpm`, `pkg_name`, `trans_item_action`; `trans.dt_begin` is a
     Unix time and `trans.description` the command line.
   - `dnf5 history list` / `history info N` also work without root.
   - Reading SQLite needs a dependency (or parsing `dnf5 history` output); owner decision.
4. **btrfs compression.** With zstd, on-disk use is ~60% of the referenced size, so "freed"
   numbers based on file sizes overstate the gain on Fedora. Only `compsize` / `btrfs fi du`
   give exact figures.
5. **Terminal detection** works, but the GNOME key pointing at a missing `xdg-terminal-exec`
   is a real trap: any code that trusts that key without checking the binary fails on Fedora.

## 5. Other facts worth keeping

- `systemd-tmpfiles`: `/tmp` 10 d, `/var/tmp` 30 d, coredump dir `2w`, `/var/cache/man` index
  cleanup; journald uses defaults (no `journald.conf`).
- `abrt` is not installed; coredumps go to systemd-coredump. Two GNOME session crashes during
  first boot were recorded (files already gone).
- dnf5 history on a fresh install: id 1–2 are image build transactions (`kiwi`), id 3 is the
  GNOME Software download (`dnf5daemon-server`).
- Fedora ships `/root/anaconda-ks.cfg` (kickstart of the install, 4 KB).

## 6. Limits

- One machine, one fresh install; a long-used Fedora will have more cache, kernels and logs.
- The 1.5 GiB offline download depends on GNOME Software's automatic updates being on and on
  the age of the ISO.
- `htop` and `mc` did not create config files in the scripted run (they only write them on
  interactive use), so only `ranger` left a leftover.
